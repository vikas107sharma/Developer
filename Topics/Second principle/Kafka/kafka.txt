⚡⚡ Asynchronous Processing ⚡⚡
======================== Background Jobs Using Application Threads ========================

Run async work inside same service process.

API Thread -> submit -> Background Thread
Pros
No extra infrastructure
Low latency
Cons
Service crash -> jobs lost
No retries/durability
Hard to scale across machines

======================== Database-Based Async (Polling) ========================

Store tasks in DB.

Order Service -> DB(task)
Worker -> poll DB -> process
Pros
Durable
Easy retries
Cons
Constant polling is inefficient
High DB load

======================== Cron Jobs / Scheduled Workers ========================

Run tasks at fixed intervals.

Cron -> every 5 mins

Use cases:
daily reports
reminder emails
cleanup jobs

Pros
Predictable
Simple
Cons
Not real-time
Bad for user-triggered events

Cron is:
Time-driven, not event-driven

======================== Webhooks ========================

Your system asynchronously calls another system's API.

Example:
Payment success -> call merchant webhook

Pros
Real-time integration
Event-driven
Cons
Network failures
Retry complexity
Receiver downtime handling

Webhooks are async but unreliable without retries/idempotency.

======================== Message Queue ========================
Producer -> Queue -> Consumer

Used for:
background jobs
retries
buffering traffic spikes

Example:
Order placed -> send email job

======================== Event Streaming ========================

Events are published and multiple consumers react independently.

Producer -> Topic -> Consumer Groups

Events remain stored and can be replayed later.

======================== Message Queue vs Event Streaming ========================
Message Queue (Todo List)
Each message = one job
One consumer processes it
Message removed after processing

Example:
Send email
Generate invoice
Resize image

Good for:
task processing
worker systems

Event Streaming (Immutable History)
Event = fact
Events are immutable
Multiple consumers can read same event
Events can be replayed

Example:
OrderPlaced
PaymentCompleted
UserSignedUp

Good for:
analytics
auditing
real-time pipelines

Events stay for retention period even after consumption.

Example:
Apache Kafka

======================== Is Kafka a Message Queue or Event Stream? ========================

Kafka is fundamentally:
Event Streaming Platform

But it can also behave like a message queue depending on consumption pattern.


✅✅ Kafka ✅✅

======================== Broker ========================

A broker is a Kafka server that stores data and serves read/write requests.
Think of a broker as:
a machine
running Kafka
storing partitions on disk

Kafka Cluster
Broker 1
Broker 2
Broker 3

One Kafka with multiple brokers = cluster.
Kafka scales by adding brokers.

To avoid single points of failure we have replicas of brokers, and partitions are also replicated internally (replication_factor).

======================== Topics ========================

Where are events stored?
Inside brokers, in partitions.

As Kafka as a system contains multiple brokers, data is stored inside brokers — specifically in partitions.

A topic is a logical thing, not physical.
A broker can contain a lot of data, even from different topics.

Inside the broker, partitions are what actually hold the events.

Topic: folder name
Partitions: actual files inside it
You cannot write data into the folder — you write data into the files.

======================== Partitions ========================

Perform hashing, then assign the event to a specific partition.
Ordering is maintained within a partition, but not across partitions.

A topic is not physical storage — it is a logical grouping.
Kafka needs physical storage, and that is what partitions are.

Why a single log (topic without partitions) doesn't work
Imagine Kafka had:
Topic: orders
(single log file)

Problems:
X No scalability
Only one broker can write
Throughput capped by one disk and one CPU
X No parallelism
Only one consumer can read efficiently
Cannot scale consumers
X No fault tolerance
If broker dies, topic gone

Kafka's goal was:
Massive throughput + horizontal scaling
That is impossible without partitions.

What partitions actually solve
1. Scalability
Each partition:
⚫ is an independent log
⚫ can live on a different broker
So Kafka scales by:
More partitions -> more parallelism -> more throughput

2. Parallel consumers
If a topic has 5 partitions:
up to 5 consumers can read in parallel (per consumer group)
Without partitions, only one consumer would be useful.

3. Fault tolerance
Partitions can be replicated across brokers.
Topic-level replication is meaningless — replication only makes sense at the partition level.

======================== Consumer Groups & Partition Assignment ========================

Consumers can read from multiple partitions, but within a single consumer group, only one consumer can read from a given partition.

Partition P
Consumer group 1 (c1, c2) -> only c1 can read from P
Consumer group 2 (c3, c4) -> only c3 can read from P

Multiple consumers can read from the same partition simultaneously, provided they belong to different consumer groups. Within a single consumer group, a partition can be assigned to at most one consumer.

Example
CG1 (c1, c2)
Topic (p1, p2, p3)

Correct
c1 -> p1, p2
c2 -> p3

Wrong (p2 assigned to both c1 and c2 in the same group)
c1 -> p1, p2
c2 -> p2, p3

Inside Kafka, a consumer cannot exist without a consumer group.

======================== Leader-Follower Replication ========================

Replication factor = 2
Partition 0:
Leader -> Broker 1
Follower -> Broker 2
Partition 1:
Leader -> Broker 2
Follower -> Broker 3
Partition 2:
Leader -> Broker 3
Follower -> Broker 1

Only the leader handles reads/writes.
Followers:
replicate data
take over if leader fails

======================== Offset Commits ========================

1. Auto Commit
Kafka commits periodically.
Easy but risky.
Problem:
Crash after commit -> message loss

2. Manual Commit (Recommended)
Commit after successful processing.
Types:
Synchronous
Asynchronous

Best practice:
process message
commit offset

======================== Delivery Guarantees ========================

Guarantee         | How
At-most-once      | Commit before processing
At-least-once     | Commit after processing (Kafka default)
Exactly-once      | Kafka transactions + idempotent producers

======================== How Do Consumers Know an Event Has Arrived? ========================

X Kafka does NOT push events
Consumers poll.
Kafka follows pull-based consumption.

Key point: the consumer doesn't get notified.
Instead:
Consumer polls periodically
If no data -> broker waits (long poll)
If data arrives -> broker responds immediately

This is called long polling.

======================== Offsets ========================

Does every event have an offset? Who assigns it?

Yes — every event has an offset.
Scope: offset is unique only within a partition.

Who assigns the offset?
The Kafka broker (leader of the partition).

How?
Producer sends a batch to the partition leader
Broker appends records to the log
Broker assigns offsets sequentially

Example:
Topic: Orders, Partition P0 (Leader Broker 1)
Log:
Offset | Event
0      | OrderCreated(101)
1      | OrderCreated(102)
2      | OrderCancelled(101)

Producers do NOT control offsets.
Offsets are purely a broker responsibility.

======================== __consumer_offsets ========================

Each record in __consumer_offsets contains:
(groupId, topic, partition) -> committedOffset

Group: payment-service
Topic: orders
Partition: 0
Committed Offset: 125

Think of it as a map:
(payment-service, orders, P0) -> 125
(payment-service, orders, P1) -> 88

======================== Why Kafka Is So Fast at Writes ========================

1. Append-only log
No random writes
Always append at end
Sequential disk writes (FAST)

2. OS Page Cache
Kafka relies on OS cache
Writes hit memory first
Disk flush happens asynchronously
Zero-copy optimizations.

3. Batching
Producers send batches, not single messages:
Fewer syscalls
Better compression
Higher throughput

4. Partitioning
Writes are spread across:
Partitions
Brokers
Disks

5. Minimal broker logic
Kafka broker does NOT:
Deserialize messages
Apply business logic
Filter per consumer
Just: append + serve + replicate

======================== How Kafka Handles So Many Reads ========================

Same reasons as writes:
Sequential disk reads
Page cache
No message deletion per read
Consumers read independently

1000 consumers reading the same data?
Disk read once, memory read many times.

======================== Pub-Sub vs Kafka ========================

Pub-Sub:
push-based model
each subscriber gets their own copy
message stays until pushed to subscriber, then removed
Hard to handle when subscriber is slow and producer is fast

Delivery Model
Aspect          | Pub-Sub         | Kafka
Delivery        | Push            | Pull
Retry           | Broker-driven   | Consumer-driven
Backpressure    | Hard            | Natural

Kafka consumers pull when ready -> built-in backpressure.

Fan-out (Multiple Consumers)
Pub-Sub:
Broker duplicates messages
Memory + network heavy
Kafka:
One copy stored
Many consumers read same data
Zero duplication

Kafka scales reads cheaply.

Message Lifetime
Aspect              | Pub-Sub         | Kafka
Message retention   | Until delivered | Time / size based
Replay              | No              | Yes
Late joiner         | Misses data     | Can replay

Consumer Independence
In Pub-Sub: broker tracks delivery.
In Kafka: consumers track their own offsets.

Throughput
Kafka is insanely fast because:
Sequential disk writes
OS page cache
Zero-copy (sendfile)
Batching
No per-message ACK to multiple consumers

Pub-Sub systems typically:
Do per-message routing
Maintain subscriber lists
Push data eagerly

Why Kafka Is Not Just Pub-Sub
Kafka intentionally breaks classic pub-sub assumptions:
Broker does NOT track per-consumer delivery
Broker does NOT delete data on consumption
Consumers are responsible for state
Storage is first-class

Kafka is closer to:
A distributed commit log + pub-sub semantics

When to Use Pub-Sub
Simple notifications
Low latency push
No need for replay
Few consumers

======================== Kafka vs RabbitMQ ========================

Kafka keeps events (event streams).
RabbitMQ works on tasks (message queue).

Kafka                          | RabbitMQ
Multiple consumers             | Single consumer per task
Pull-based (consumer polls)    | Push-based
Time-based retention           | Removed once task ACKed

Feature         | Kafka       | RabbitMQ
Model           | Event log   | Message broker
Push vs Pull    | Pull        | Push
Replay          | Yes         | No
Retention       | Time-based  | Until ACK
Throughput      | Very high   | Moderate
Scaling         | Horizontal  | Limited
Consumer State  | Consumer    | Broker
Best For        | Streaming   | Tasks
