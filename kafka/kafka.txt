A partition is an ordered append-only log.

Perform hashing, then assign the event to a specific partition.
Ordering is maintained within a partition, but not across partitions.

A topic is not physical storage — it is a logical grouping.
Kafka needs physical storage, and that is what partitions are.

======================== Consumer Groups & Partition Assignment ========================

Consumers can read from multiple partitions, but within a single consumer group, only one consumer can read from a given partition.

Partition P
Consumer group 1 (c1, c2) -> only c1 can read from P
Consumer group 2 (c3, c4) -> only c3 can read from P

Multiple consumers can read from the same partition simultaneously, provided they belong to different consumer groups. Within a single consumer group, a partition can be assigned to at most one consumer.

Example
CG1 (c1, c2)
Topic (p1, p2, p3)

Correct
c1 -> p1, p2
c2 -> p3

Wrong (p2 assigned to both c1 and c2 in the same group)
c1 -> p1, p2
c2 -> p2, p3

Inside Kafka, a consumer cannot exist without a consumer group.

Consumer lag:
Producers are producing at much higher rate than consumers.

======================== Leader-Follower ========================

For every partition, one replica is the leader.
The others are followers.

======================== ISR — In-Sync Replicas ========================

ISR = {Broker 1, Broker 2, Broker 3}
Broker 3 becomes slow:

Broker 1 → Leader       ✅
Broker 2 → Replica      ✅
Broker 3 → Replica      ❌ slow

Kafka can remove Broker 3 from ISR:

ISR = {Broker 1, Broker 2}

If the leader dies, Kafka can select an eligible in-sync replica as the new leader.

======================== KRaft ========================

"What is KRaft in Kafka?"
KRaft is Kafka's built-in consensus mechanism for managing cluster metadata. Kafka maintains a controller quorum using the Raft protocol, with one active controller and replicated metadata logs. The controller manages things like broker membership and partition leadership, and when a controller fails, another controller can be elected from the quorum.

"What is the metadata log?"
It's an ordered, replicated log containing Kafka cluster metadata changes, allowing controllers to maintain a consistent view of the cluster state.

Kafka uses the Raft consensus protocol for its metadata quorum.

Instead of:

Kafka
  ↓
ZooKeeper

modern Kafka can use:

  ↓
KRaft controller quorum

The controllers maintain the cluster metadata.

That metadata needs to be coordinated consistently.

======================== Broker vs Controller ========================

This distinction is important.

A broker handles data-plane work:

produce
consume
store
replicate

Producer ──(Publishes)──► [   BROKER   ] ──(Fetches)──► Consumer 1 ──► Application
                          [  Topic P2  ]                      
                          [ Log: 100.. ]
                          [ Offset:102 ]

Role of the Broker:

Storage & Persistence: Stores records 100, 101, and 102 sequentially on disk inside partition P2.

Offset Tracking: Receives and saves the consumer group's committed offset (102).

Fetch Handling: Serves records to Consumer 1 when requested and updates what has been delivered.

Failover Coordination: When Consumer 1 crashes, the broker detects the failure (via missed heartbeats), rebalances the group, and tells the new consumer to resume fetching starting at offset 103 (the next uncommitted offset).



Broker's Role in Delivery Semantics

The delivery semantic (At-Least-Once, At-Most-Once, or Exactly-Once) depends directly on when the consumer tells the broker to update the committed offset relative to processing:

At-Least-Once (Most Common): The consumer reads records 100–102, completes application processing, and then sends the commit for 102 to the broker. If it crashes after processing but before committing, the broker still holds offset 99. The new consumer fetches 100–102 again, causing duplicate processing.

At-Most-Once: The consumer fetches 100–102, immediately commits offset 102 to the broker, and then processes them. If it crashes mid-processing, the broker already saved 102, so the new consumer resumes at 103, missing the unprocessed records.

Exactly-Once: The broker works with producers and consumers via transactional APIs to write records and commit offsets together atomically.

The controller handles cluster coordination:

leader assignment
broker membership
metadata
partition state

Modern Kafka deployments can use separate controller roles or combined broker/controller roles depending on configuration.

======================== What happens when a broker dies? ========================

Suppose:
P0
Broker 1 → Leader
Broker 2 → Replica
Broker 3 → Replica

Broker 1 crashes.
Controller detects the broker failure.
Broker 1 ❌

Controller determines:
P0 needs a new leader

It selects an eligible replica:
Broker 2 → New Leader
Broker 3 → Replica

Metadata is updated.
Producers/consumers refresh metadata and start communicating with Broker 2.

The important point:
The controller doesn't move every message manually. It coordinates leadership and replica state; brokers handle the actual data replication.

======================== What happens when a consumer dies? ========================

Different problem.

P0 → C1
P1 → C2
P2 → C3

C2 ❌

Consumer group coordination detects the failure.
A rebalance occurs:
P0 → C1
P1 → C3
P2 → C3

The new consumer continues from the group's committed offsets.

So remember:

Broker failure
→ Controller / partition leader election

Consumer failure
→ Consumer group rebalance
