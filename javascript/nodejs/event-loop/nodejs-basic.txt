1. Callbacks (Inversion of Control)
A Callback is a function passed into an asynchronous function to be invoked when the operation completes.

The Problem: It suffers from Inversion of Control—you hand over execution authority to a third-party function, meaning you can't guarantee if or how many times your callback gets called. It also leads to deep nesting—or Callback Hell—making code difficult to maintain and error handling clunky via the (err, result) convention.

You give your code to getUser and say: "Here is my function, you invoke it whenever you are ready."

The Problem: You lose control. If getUser has a bug, it might invoke your function zero times, multiple times, or run it synchronously by mistake.

// ❌ 1. Callback: Nested & Inversion of Control
getUser(id, (err, user) => {
  if (err) return handleError(err);
  getOrders(user.id, (err, orders) => { /* ... */ });
});

// 1. Get user -> 2. Read file -> 3. Send email -> 4. Log to DB
db.query('SELECT * FROM users WHERE id = 1', (err, user) => {
    if (err) return res.status(500).send('DB Error');

    fs.readFile('/templates/welcome.txt', 'utf8', (err, template) => {
        if (err) return res.status(500).send('FS Error');

        const emailBody = template.replace('{{name}}', user.name);
        
        emailService.send(user.email, emailBody, (err, response) => {
            if (err) return res.status(500).send('Email Error');

            db.query('UPDATE users SET email_sent = 1 WHERE id = 1', (err, result) => {
                if (err) return res.status(500).send('DB Update Error');
                
                res.status(200).send('Success');
            });
        });
    });
});


2. Promises (Reclaiming Control)
A Promise solves this by returning a stateful object—pending, fulfilled, or rejected—that acts as a proxy for a future value.

Instead of handing your function to getUser, getUser immediately hands you a Promise object (a placeholder/receipt for future data).

You attach .then(callback) to that receipt:

The Difference: getUser doesn't call your function anymore. The V8 JavaScript engine itself monitors the Promise object. Once the Promise changes status from pending to fulfilled, the JS engine places your .then() callback into the Microtask Queue and invokes it safely exactly once.

How it Works: Instead of passing a callback in, the function returns a Promise that you listen to via .then() and .catch().

The Key Advantage: It reclaims control flow, supports composition methods like Promise.all(), and executes callbacks via the Microtask Queue, guaranteeing they run after the current call stack completes.
// 🟡 2. Promise: Stateful & Microtask Queue
getUser(id)
  .then(user => getOrders(user.id))
  .then(orders => console.log(orders))
  .catch(handleError);


3. Async/Await (Syntactic Sugar over Promises)
Async/Await is syntactic sugar built on top of Promises and Generators.

How it Works: Mark a function async, and you can await any Promise. V8 pauses execution at the await statement, yields back to the main thread non-blockingly, and resumes once the microtask resolves.

Under the hood, async/await is still using Promises. It does not change how Node.js handles async operations; it just gives you a cleaner syntax so you don't have to write long .then() chains.

It pauses execution of that specific function, not the entire application or thread.

It returns control to the main event loop immediately so Node can handle other incoming HTTP requests, timers, or I/O.

The Key Advantage: It lets us write non-blocking asynchronous code using familiar, synchronous imperative syntax, allowing us to use standard try/catch blocks for clean, unified error handling."
try {
  const user = await getUser(id);
  const orders = await getOrders(user.id);
  console.log(orders);
} catch (err) {
  handleError(err);
}


1. Promise.all() (all-or-nothing)
Fulfills when ALL promises resolve successfully. Rejects immediately if ANY promise rejects (short-circuit on first error).
Resolves with an array of values matching the input order, or rejects with the first error reason.
const [user, settings] = await Promise.all([
  getUser(id),
  getSettings(id)
]);


2. Promise.allSettled()
Waits for ALL promises to complete, regardless of whether they fulfill or reject (never short-circuits on rejection).
Resolves with an array of result objects describing each outcome: { status: 'fulfilled', value } or { status: 'rejected', reason }.
const results = await Promise.allSettled([
  sendEmail(user1),
  sendEmail(user2)
]);
// Safe to iterate: check status === 'fulfilled' or 'rejected'


3. Promise.any()
Fulfills as soon as ANY promise fulfills (first success). Ignores rejections unless ALL promises reject.
Resolves with the first fulfilled value. If all fail, it rejects with an AggregateError containing all rejection reasons.
try {
  // Returns result from whichever mirror responds successfully first
  const data = await Promise.any([
    fetchFromCDN1(),
    fetchFromCDN2()
  ]);
} catch (err) {
  // AggregateError: All promises were rejected
}

4. Promise.race()
Settles as soon as ANY promise settles—whether it fulfills OR rejects (first to cross the finish line wins).
// Times out if fetch takes longer than 5 seconds
const timeout = new Promise((_, reject) => 
  setTimeout(() => reject(new Error('Timeout')), 5000)
);
const data = await Promise.race([
  fetchData(),
  timeout
]);

━━━━━━━━━━━━━━━ Closure ━━━━━━━━━━━━━━━
A closure happens when an inner function references variables declared in its outer function.

Normally, when a function finishes executing, its local variables are popped off the call stack and garbage-collected.

However, if an inner function still holds a reference to those variables, the V8 engine moves them from the stack to the heap, keeping them alive.
The inner function remembers its lexical environment.

Example:
Why this is good: It prevents you from hardcoding business logic inside the route handler or relying on global variables. The configuration is injected once and retained in memory.

// The outer function takes the configuration (allowedRole)
const authorizeRole = (allowedRole) => {
    
    // The inner function is the actual Express route handler.
    // It forms a closure over 'allowedRole'.
    return (req, res, next) => {
        const userRole = req.user.role; 

        if (userRole !== allowedRole) {
            return res.status(403).json({ error: `Requires ${allowedRole} access.` });
        }
        
        next();
    };
};

// 'adminAuth' is now a function that will forever remember allowedRole = 'admin'
const adminAuth = authorizeRole('admin');
const salesAuth = authorizeRole('sales_officer');

app.post('/api/settle-cheque', salesAuth, controller.settleCheque);


Memory Leaks Due to Closures
Because closures prevent the Garbage Collector (GC) from clearing captured variables, they are a primary source of memory leaks in long-running Node.js processes.


Why does Closure exist?
Without closures, asynchronous programming in Node.js would be impossible. When you make a database query and pass a callback, that callback is executed seconds later in a completely different tick of the event loop. If closures didn't exist, the callback would have no way to remember the req or res objects from the original request scope to send the data back to the user.

// OUTER FUNCTION (Route Handler)
app.get('/user/:id', (req, res) => {
    const userId = req.params.id;      // Local variable in outer function
    const requestTime = Date.now();    // Local variable in outer function

    // INNER FUNCTION (Database Callback)
    const dbCallback = (err, userData) => {
        // Look where these 3 variables came from:
        if (err) return res.status(500).send('Error'); // 'res' is from the outer scope!
        
        const duration = Date.now() - requestTime;     // 'requestTime' is from the outer scope!
        res.json({ data: userData, duration, requestedId: userId }); // 'userId' is from the outer scope!
    };

    db.query('SELECT * FROM users WHERE id = ?', [userId], dbCallback);
});
