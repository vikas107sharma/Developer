━━━━━━━━━━━━━━━ 🧠 V8 vs Libuv ━━━━━━━━━━━━━━━

The Event Loop is the design pattern (the concept).
Libuv is the engine (the implementation) that runs it in Node.js.

🧠 V8 (C++): executes your JavaScript.
💪 Libuv (C++): handles everything that isn't JS — file reads, network packets, timers.

The "Node.js Event Loop" IS the Libuv event loop.

🔹 How Libuv beats single-threaded limits
JS runs on one thread, but real apps need many things at once.
🌐 OS Kernel: network I/O (sockets, API calls) is handed to the OS (epoll/kqueue/IOCP). OS is multi-threaded.
🧵 Thread Pool: tasks the OS can't do async (fs, crypto, zlib) run on Libuv's internal worker threads.

🔹 Cross-platform wrapper
Each OS does I/O differently (Windows IOCP, Linux epoll, macOS kqueue).
Libuv wraps them all -> you write fs.readFile() once, it works everywhere.

  Component    | Role       | Responsibility
  ------------ | ---------- | ----------------------------------------
  V8 Engine    | Translator | Turns JS into machine code
  Libuv        | Manager    | Runs the Event Loop + Thread Pool
  Event Loop   | Scheduler  | Picks which callback runs next
  OS Kernel    | Worker     | Performs the disk/network operations


━━━━━━━━━━━━━━━ 🚀 Execution Lifecycle ━━━━━━━━━━━━━━━

Run `node index.js` -> one OS process + one Main Thread (V8).

🔹 Synchronous phase (Main Thread)
Runs top to bottom, once:
init environment
execute top-level sync code
require/import modules
register async callbacks (timers, I/O listeners)

🔹 Event Loop starts
Only after the call stack is EMPTY.
The loop is an orchestrator — it offloads, it does not run heavy work itself:
🌐 Network I/O  -> OS Kernel
🧵 fs / crypto / zlib -> Libuv Thread Pool


━━━━━━━━━━━━━━━ 🔁 The 6 Phases ━━━━━━━━━━━━━━━

   ┌───────────────────────────┐
   │           timers          │  setTimeout / setInterval
   └─────────────┬─────────────┘
                 v
   ┌───────────────────────────┐
┌─>│     pending callbacks     │  deferred I/O callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │       idle, prepare       │  internal only
│  └─────────────┬─────────────┘      ┌───────────────┐
│  ┌─────────────┴─────────────┐      │   incoming:   │
│  │           poll            │<─────┤  connections, │
│  └─────────────┬─────────────┘      │   data, etc.  │
│  ┌─────────────┴─────────────┐      └───────────────┘
│  │           check           │  setImmediate()
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
└──┤      close callbacks      │  socket.on('close', ...)
   └───────────────────────────┘

🔹 poll: the important one — retrieves new I/O events, runs most I/O callbacks, blocks here when idle.

🔹 Priority order between phases
process.nextTick()  -> always wins
setTimeout()        -> timers phase
setImmediate()      -> check phase

📚 nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick


━━━━━━━━━━━━━━━ 🧵 The Thread Pool ━━━━━━━━━━━━━━━

Default: UV_THREADPOOL_SIZE = 4 (configurable up to 128).
One process holds: 1 Main Thread + 4 Worker Threads, sharing your CPU cores.

🔹 The bottleneck
Push 5 heavy tasks -> first 4 grab the threads, 5th waits in queue
until a worker frees up.

  const crypto = require('crypto');

  // 1-4: picked up immediately by the 4 workers
  crypto.pbkdf2('pw','salt',10000,1024,'sha512',()=>console.log('1'));
  crypto.pbkdf2('pw','salt',10000,1024,'sha512',()=>console.log('2'));
  crypto.pbkdf2('pw','salt',10000,1024,'sha512',()=>console.log('3'));
  crypto.pbkdf2('pw','salt',10000,1024,'sha512',()=>console.log('4'));

  // 5: waits until one of 1-4 finishes
  crypto.pbkdf2('pw','salt',10000,1024,'sha512',()=>console.log('5'));

💡 Heavy on crypto/fs? Raise UV_THREADPOOL_SIZE at startup (match CPU cores).


━━━━━━━━━━━━━━━ ⚖️ CPU-Bound vs I/O-Bound ━━━━━━━━━━━━━━━

💻 CPU-Bound — blocks the main thread
CPU works at 100% to compute something.
Examples: bcrypt, JSON.parse on huge payloads, image/video processing, giant loops.
-> Runs on V8's single thread. Too slow = the whole server freezes.

🌐 I/O-Bound — offloaded, non-blocking
CPU just waits for external data.
Examples: DB queries, fs.readFile, axios, incoming HTTP.
-> Libuv sends these to the OS Kernel or Thread Pool. Main thread stays free.


━━━━━━━━━━━━━━━ ⚠️ When You Need worker_threads ━━━━━━━━━━━━━━━

Waiting on OS/Network (I/O)          -> Automatic (Kernel/epoll)
Waiting on built-ins (fs, crypto)    -> Automatic (Libuv Thread Pool)
Heavy CUSTOM math/loops in JS        -> Manual (worker_threads REQUIRED)

⚠️ `async` does NOT make CPU work non-blocking — it still runs on the main thread:

  async function calculateMillions() {
      let sum = 0;
      // Freezes the Event Loop until this finishes.
      for (let i = 0; i < 1_000_000_000; i++) sum += i;
      return sum;
  }


━━━━━━━━━━━━━━━ 🌍 Browser vs Node.js ━━━━━━━━━━━━━━━

🔹 Who provides the loop
🖱️ Browser: Web APIs (DOM, XMLHttpRequest, timers) from Chrome/Firefox.
🖧 Node.js: Libuv — DB connections, HTTP requests, file reads. No UI/Window needed.

🔹 Background worker
Browser -> Web APIs.
Node.js -> C++ bindings -> Libuv -> OS Kernel (network) or Worker Pool (fs/crypto).

🔹 Callback queues
Browser -> one Task Queue + one Microtask Queue (Promises).
Node.js -> multi-stage phased architecture (the 6 phases above).

✅ Even a plain terminal script starts an event loop to wait on async work.
